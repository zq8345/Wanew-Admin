# 契约：admin 的写入路径 —— 「白名单」在这个仓里有**两种相反的语义**

**发起方**：wanew-admin · 仓 `zq8345/Wanew-Admin` · 路径 `docs/contracts/product-json-write-paths.md`
**读者**：任何要往 admin 写的 JSON 里加字段的人（官网窗口、多语言窗口、以及未来的我）
**为什么单独成文**：差异**只在特定操作之后才显现**，而做那次操作的人不会把两件事联系起来——"我明明什么都没改，怎么少了个字段"。

---

## ⭐ 先读这条：看到"白名单"三个字，**先问它管的是哪一件事**

| 文件 | 白名单管的是 | 机制 | 未知字段的下场 |
|---|---|---|---|
| `data/products/*.json` | **什么能活下来** | 按白名单**重建**对象 | **被丢掉** |
| `data/contact-info.json` | **什么能被编辑** | **深拷贝**原文件 + 选择性覆盖 | **活着，只是改不动** |

```js
// products：重建 —— 名单外的东西不存在
const out = { id, category, form, status, /* …白名单… */ };

// contact：深拷贝 + 覆盖 —— 名单只决定"谁能被改"
const merged = JSON.parse(JSON.stringify(contactJson));
for (const e of edits) merged[e.key] = e.value;   // e.key 必须在 CONTACT_KEYS 里
```

**同一个词、同一个仓、相邻的两个函数，对未知字段的后果完全相反。**
所以「admin 会不会保留未知字段」**没有统一答案**——而如果谁给出一个统一答案，这两件事必有一件会出错。

推论（各自的行动不同）：
- **products**：加字段要**先找 admin 加进白名单**，否则保存即消失。
- **contact**：加字段**不会丢**；但**从名单里摘掉一个键 = 从此没有任何入口能改它，包括 API**。
  摘 UI 控件而不摘 `CONTACT_KEYS`，就留下**一条只有 API 能走的暗路**——照样能往官网不消费的字段里写值。

> 已按此摘除 `hours` / `response`（官网联系页不消费；模板里 `cfg.hours` 唯一一处在 HTML 注释里）。
> **两侧同时摘，且数据原样留在文件里**（深拷贝语义），等官网侧删除数据。
> 顺序是刻意的：**先摘控件、后删数据**。反过来会开一个窗口期——Joe 看到两个空输入框、填了、写回 JSON、
> 而官网不消费，**页面纹丝不动**。死字段没人看得见，**能填的输入框会主动骗人**：等他发现不一致时，查的方向已经全错了。

---

## 一句话

> **同一个产品，走「批量操作」不会丢未知字段，走「编辑页保存」会丢顶层和 `i18n.en` 里的未知字段。**

---

## 两条路径

### 路径 A：编辑页保存 —— `POST /api/admin/products` · `PUT /api/admin/products/:id`
经 `validateProduct()`，**按白名单重建对象**。分三层，各不相同：

| 层 | 行为 | 后果 |
|---|---|---|
| `i18n.<语种>` 整体 | **保留**（`{...existing.i18n}` 打底，只重建 `en`） | ✅ 加**新语种**安全（zh/ja/… 随便加） |
| `i18n.en` 内部 | **白名单** | ⚠️ 往 en 里加字段 → **保存后消失** |
| JSON 顶层 | **白名单** | ⚠️ 往顶层加字段 → **保存后消失** |

**白名单实际内容（实测打印，非凭记忆）**
- 顶层：`id, category, form, status, robots, i18n, images, jsonld_product, jsonld_breadcrumb`
  （另有两个**非空才落盘**：`compatible_with`、`videos`）
- `i18n.en`：`title, summary_html, description_html, meta_description`
  （另有两个**条件落盘**：`meta_title`（≠title 时）、`card_title`（非空时））

### 路径 B：批量操作 —— `PUT /api/admin/products/bulk`
`JSON.parse(原文件)` → **只改 `status` / `category` / `form` 其中一个字段** → 写回。
⇒ **未知字段全部保留**（顶层、`i18n.en` 内、任何语种都保留）。

---

## 所以要加字段的话

| 想加在哪 | 安全吗 | 要做什么 |
|---|---|---|
| **新语种** `i18n.zh` 等 | ✅ 安全 | 直接写，无需通知 |
| **`i18n.en` 内新字段** | ❌ 会被丢 | **先找 admin 加进 en 白名单** |
| **JSON 顶层新字段** | ❌ 会被丢 | **先找 admin 加进顶层白名单** |

**"admin 保留未知字段"这句话是错的** —— 它只在 `i18n` 的语种那一层成立。

---

## 为什么会长成这样（留给后来者）

`i18n` 那层当初写成 spread 打底，目的是**防翻译被擦除**（注释原文："旧翻译打底，es/pt 等原样保留"）。
**一个当年为了别的目的做的正确设计，今天免费挡下了 zh 被抹掉的风险。**
而顶层与 `i18n.en` 是白名单，没有这层保护。**同一个文件里两种策略并存，读代码的人只会看到自己碰到的那一半** —— 所以写在这里。

---

## 已排期的改动（未实施）

`/products/` URL 迁移需要存 **slug 历史**（旧网址段留档、自动 301），那是一个**顶层字段**。届时：
- **顶层改成 spread 打底**（`{...existing, ...白名单字段}`）—— 小改、收益直接。
  代价：admin 从此会把官网写的任何顶层字段原样带回，**删字段就得由官网侧改**，不能靠 admin 丢弃。
- **`i18n.en` 维持白名单**。它是**唯一由后台表单编辑的语种**，全保留意味着"表单里没有的字段永远删不掉"（例如想清空 `card_title`）——**需要先设计一个显式删除的表达方式**，这是设计问题不是实现问题。

**在那之前，上表的规则有效。**
