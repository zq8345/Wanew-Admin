# 图片管线：先量（未改任何东西）

**做的事**：只测量，不动代码。对象是**用户真实要下载的那些字节**，不是桶统计。
**结论先说**：**原 brief 的优先级要换** —— ①webp 化基本已完成且不是瓶颈，**②缩略图（限尺寸）才是最大收益**。

---

## 1. 测量方法与材料校验

- 取 `data/products-index.json` 的 68 条 `thumb` —— 这**就是** `/products/` 列表页一次要加载的图。
- 逐个 HEAD 拿真实 `content-length` / `content-type`。**68/68 有效**（先断言材料有效再统计；有效率不足 80% 直接拒绝出结论）。
- 尺寸取自官网 `data/media-sizes.json`（883 条）。

> ⚠️ 中途踩到并修正的一个错：缩略图有**两种形态** —— 绝对 `https://img.wanew.com/…` 与根相对 `/static/…`。第一版把根相对也拼到图床上 → 40 个 404。**那不是"图不存在"，是我解析错了**；材料有效性断言把它拦下来了（28/68 有效 → 拒绝出结论），没有拿着假数据往下走。

## 2. 现状（实测）

单张：中位 **95KB** · p90 **185KB** · 最大 **339KB**

## 3. ⭐ 真正的瓶颈：不是格式，是**像素尺寸**

| | 数值 |
|---|---|
| 有尺寸数据的缩略图 | 40 / 68 |
| 自然宽度 | 中位 **1500px**（最小 800 · 最大 2000） |
| 卡片实际显示宽 | 约 **300px**（`col-xl-3` 四列栅格） |
| **超过显示宽 1.5 倍的** | **40 / 40（全部）** |
| 平均超出 | **4.4× 线性 ≈ 19× 面积** |
| **粗估可省** | **~3.11 MB / 6.53 MB（约 48%）** |

最浪费的几张（**全是已经 webp 化的**）：
```
260KB  1920×1920  (6.4×显示宽)  webp
212KB  2000×2000  (6.7×显示宽)  webp
194KB  1600×1600  (5.3×显示宽)  webp
```

**这就是为什么 webp 化没换来速度**：把 2000px 的图压成 webp，它仍然是一张 2000px 的图。**格式省的是每像素的字节，尺寸省的是像素数本身，后者在这里大一个量级。**

---

## 4. 所以优先级应该换（原 brief vs 实测）

| | 原 brief | 实测后建议 |
|---|---|---|
| 1 | 上传时生成 webp + 限长边 | **生成缩略图供列表卡用**（~3.1MB / 48%，且不动任何现有 URL） |
| 2 | 生成缩略图供列表卡用 | **补 R2 那 28 张的尺寸元数据**（防 CLS，官网侧已在用 `media-sizes.json`） |
| 3 | 回写宽高元数据 | **上传时限长边 + webp**（治未来新图，存量收益已被 ① 覆盖大半） |

**关于 brief 里那个「最大单图 3.3MB」**：列表页最大的一张只有 **339KB**。3.3MB 那张在**详情页**，不在列表卡 —— 两者要分开算，别用详情页的数字给列表页排优先级。

---

## 5. 顺带量到的两个缺口

- **尺寸元数据覆盖 40/68**：R2 那 28 张**全无**。官网靠 `media-sizes.json` 给 `<img>` 注 width/height 防 CLS，这 28 张目前注不上。
- **R2 侧 23/28 仍是 jpeg**：这部分 webp 化确实还有收益，但**排在限尺寸之后**。

---

## 6. 目标长边：实测 **920px**（不是 600，也不是 720）

在**线上真实 `/products/`** 上扫了 10 个视口宽度，量卡片图的**实际渲染宽**：

| 视口 | 卡片宽 | 列数 |
|---|---|---|
| 414 | 344 | 1 |
| 480 | 410 | 1 |
| 520 | 450 | 1 |
| **530** | **460** | **1 ← 最大** |
| 539 | 216 | 2 |
| 575 | 234 | 2 |
| 767 | 330 | 2 |
| 991 | 277 | 3 |
| 1199 | 250 | 4 |
| 1920 | 264 | 4（容器封顶，不再增长） |

**⭐ 最大渲染宽 = 460px，出现在视口 530px 处（单列的上边界）。**

**它不在任何一个极值端**：最宽视口 1920 只有 264px、常见手机宽 414 是 344px。**只测两个极值会得到 344px → 长边 688 → 而 530px 视口下的用户拿到的是糊的。**

> 布局在**带内**列数固定、卡片宽随视口单调增 ⇒ **每条带的最大值必在带的上边界**。所以扫的是各带上边界 + 二分找带的切换点（520 单列 / 539 双列 → 边界在其间），不是均匀撒点，也不是只取两端。

**结论：长边取 `460 × 2 = 920px`。** 建议落 **960px**（留余量、取整）。
`600`（按 300px 估算）和 `720`（按 360px 估算）**都不够** —— 两者都会让 530px 视口下的单列卡片变糊。

2. 缩略图的 key 约定 —— 必须**不动现有 URL**（`<base>.thumb.webp` 之类新增而非替换），老图无缩略图时**回落原图**。
3. ~~目标尺寸~~ **已实测：920px（见 §6），建议落 960px**。详情页那一档**先量再做**。

**先量的价值**：如果按原 brief 直接开做 ①，会把力气花在**已经做完的事**上，而真正的 48% 一直留在那儿。

## 8. ⭐ 结果（改造后实测·同一把尺子）

口径不变：**页面实际要下载的字节**，不是"生成了多少个文件"。同一个脚本、同一个 products-index、同样先断言材料有效（68/68）。

| | 改造前 | 改造后 | |
|---|---|---|---|
| **列表页图片总下载** | **6.53 MB** | **2.96 MB** | **−3.57 MB（−55%）** |
| 单张中位 | 95 KB | **42 KB** | −56% |
| 单张最大 | 339 KB | **164 KB** | −52% |
| `wanew.com` `/static/`（官网侧 40 张） | 3.26 MB | 1.70 MB | −48% |
| `img.wanew.com` R2（本仓侧 28 张） | 3.27 MB | **1.26 MB** | **−61%** |
| R2 侧格式 | jpeg×23 · webp×5 | **webp×28** | — |

**§3 的预估是 ~48%，实测 55%** —— 预估偏保守，因为它只算了像素数，没算 R2 那 23 张 jpeg→webp 的叠加收益。

> ⚠️ 这个数**在清单合并进官网并跑完 regen 之后才成立**。在那之前文件已经躺在 R2 里，
> 而页面一个字节都没少下 —— **"生成了 28 个文件"和"用户少下载了 2MB"是两回事**。

## 9. 清单谁写、什么时候写（`data/r2-thumbs.json`）

**上传路径只创建对象，不写清单。** 理由：清单必须由**枚举真实存在的对象**产生，而"我刚 PUT 了所以它存在"是**意图**——PUT 成功而清单提交失败，两边就永远对不上，且**没有症状**。

| | 谁 | 什么时候 |
|---|---|---|
| 生成缩略图对象 | 回填脚本（存量）／浏览器上传（新图） | 各自当场 |
| **写清单** | **只有 `scripts/r2-thumbs.mjs` 生成模式** | 人工跑，产出提交到官网仓 |
| **发现清单没跟上** | `node scripts/r2-thumbs.mjs --check <清单路径>` | 发版前 |

**代价是有个真实缺口**：新上传的图有缩略图文件、清单里还没有 → regen 回落原图 → 新图享受不到优化，**且无症状**。
`--check` 就是把这个缺口**变成会出声的**。它不修，只吼，三个方向各查一遍：

- 有文件、清单没有 → 白生成（回落原图）
- 清单有、文件没有 → regen 指向 404
- 页面正在用、对象不存在 → 列表页图裂了

> ⚠️ 这个闸的第一版**在两个已知该红的状态下都印了绿**。原因：它假设 products-index 的 `thumb` 永远是原图、
> 再去派生 `.thumb.webp`；而接管上线后 `thumb` **本身已经是缩略图** → 派生出 `xxx.thumb.thumb.webp`，
> 一个永远不存在、也永远不在清单里的 key，**两个判据同时落空 → 全绿**。
> 而"清单里有野条目"那种漂移，只遍历 products-index 派生的 key **根本碰不到**，必须遍历清单自己。
> **闸写完必须在已知绿和已知红两个状态下各跑一次** —— 否则装的是个会印✅的装饰。
